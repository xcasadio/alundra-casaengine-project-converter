## Decompilation versus binary

Rows 1 to 4 and 6 of the report's diff table were re-checked and stand: the 3-iteration spark loop, the single `sra 0x14`, one draw per loot row, the 0x78 store, and the `<=` loop bound. Label disagreements I did not re-check: the 0x86 "Add" label and the damage entry named `FindWarpFacingDirection`.

The decompilation itself was not re-read for rows 9 to 13 above. If it treats only `0x80` as "no damage", or reads `g_balanceAnimIndex` live, it differs from the binary on those points.

## Behaviour the report missed

1. **Latched hero animation.** `g_balanceAnimIndex` is written only in the hit pass of tick N and read in tick N+1. Use the latched value, not the hero's current animation.
2. **The 0xC0 response.** The hit pass treats it as a hit (sets `TouchingEntity`, so the D program runs), but `ResolveBalanceTarget` applies no damage.
3. **Death starts one tick late.** It is tested only on a tick without damage (0x80031C98 jumps over 0x80031CA0).
4. **Two hurt-path details.** The normal hurt path calls 0x8003634C (some active item/effect is cancelled; meaning UNKNOWN). The `controlFlags==0x20` path only sets the 0x78 counter.
5. **Who takes part in the hit lists.** List membership for hits and display is status 2 or 3, and for hits also `+0x20==0`. The events loop excludes slot 0. The program dispatch loop repeats until no program is pending.
6. **E beats D.** A hit coinciding with an E trigger is lost.
7. **Hazard tiles bypass armour.** They apply a raw cost of 0 to 3 HP.
8. **Multi-target hits.** An attacker can hit several targets per tick. One target accepts only the first attacker in list order: its +0x1D0 = 0x19 makes it skip later attackers in the same tick.
9. **The hit pass has a debug branch.** When `[0x800DC058]<0` and `[+4]&0x800`, it calls a printf-like routine at 0x80082918. Ignore it.
10. **Loot details.** Items 0x26, 0x51 and 0x52 can be vetoed (0x80032A00). Spawned items get +0x278 = 0x258 or −1 (a lifetime, by INFERENCE) from `0x800C5F7C`.
11. **Sprint preparation sound.** Animation 0x29 has its own effect case (0x8002FB6C) that plays a slope-dependent sound every 8 frames. This matters for the sprint slice.

## Open questions for the author

1. The response value 0xC0 means "touched, so the D program runs, but no damage". Should the port reproduce that split exactly? The binary says yes.
2. Should death keep the one-tick delay of the original, or start on the tick of the killing hit? The binary delays it, and following it is the default rule.

## Suggested slice boundaries

The report's H0 to H7 split still holds, with these refinements:
- **H1:** latch `g_balanceAnimIndex` in the hit pass. Build the hit list with the status 2/3 and `+0x20==0` filter. Apply the 0xC0 nuance.
- **H5:** include the call to 0x8003634C (needs a short discovery of its own), the `controlFlags==0x20` path, and the one-tick-late death test.
- **H2:** include the item veto at 0x80032A00 and the spawned item's fields +0x274, +0x278 and +0xB8.
