# Adversarial binary check: hero SPRINT report

Everything below was decoded from `ALUN_CD.EXE` (France) with capstone at file offset 0x800 + addr − 0x80020000. Hero base is 0x80127D30, so +0x88 = TargetAnimationId (0x80127DB8) and +0x8C = TargetDirection (0x80127DBC). Pad struct base is 0x80126F18: +0x10 is the hold word (0x80126F28) and +0x12 is the edge word.

In the MovePlayer prologue (0x80031CD4–0x80031CF8) the binary loads `s3 = hold>>12` (`00029b02 srl s3,v0,0xc`) and `s1 = dirTable[s3]` from 0x80022C6C. When the entry is −1, `s1` takes the current +0x8C (`8e11008c`).

## Behaviour the report missed

1. **CheckEntityInteraction 0x8002E910** (push, carry and similar interactions; it reads `+0x130`, the collided entity) runs only in the Idle/Moving case. PrepareSprint, Sprint and StopSprint never call it. This settles the report's unknown "pushing blocks while sprinting": FACT, there is no push or interaction from the sprint states. In Idle/Moving, a non-zero interaction result also blocks the Triangle entry on that tick.
2. **Calls before every land-state switch.** Each tick on a land slope calls 0x8002F49C (UpdatePlayerWeaponEffect), 0x8002F768 and 0x8002F884(a0 = 0) at 0x80031D68–0x80031D78, in that order, before the anim switch. The new task has to keep this order.
3. **Early-outs in the MovePlayer prologue that take priority over every sprint state:**
   - `jal 0x80031A68 ≠ −1` (0x80031C44) gives anim 0x31, or 0x3A on slope 4, plus `+0x1CC = 0x78`.
   - `+0x14 == 0` goes to 0x800327A4.
   - `+0x188 & 0x80` goes to 0x80032768.
   - `+0x20 ≠ 0` ends the tick (0x80031BAC).
   - Global `0x800DC4B8 & 0x34` gives the locked branch: CreatePlayerAnimationEffects(1) and no state machine.
   - INFERENCE: the first item is the damage or knockback entry. I did not decode 0x80031A68.
4. **SprintDash group handler 0x80031E18:** when airborne it writes **0x2D**, not a generic "Jump". It then calls TryUseItem at 0x80032680 and **ignores its result** (`j 0x80032914`).
5. **Swim switch 0x8003260C** (slope 4) clears `0x80126FFC` and `0x80127110`, calls 0x8002F884(a0 = 2), and then switches through the table at 0x80022E7C.
6. **Walk footsteps** use a different table: anims 1 and 7 → 0x8002FE24, `FrameCounter & 0xF` (every 16 ticks), sound from 0x800227F4 = [0,20,18,16,0,0,0,0,…]. This is relevant if SP2 covers walking.
7. **Dust effect id `a1 = 0`** (map header byte 0xA = 0) skips the dust spawn on land: `beqz a1` at 0x8002FC30 and 0x8002FF14.

## Decompilation versus binary (checked here)

- Bounce exit while airborne: the binary stores `+0xAC` (= 1, Moving). The decompilation writes Jump (`PlayerManager.cs:769-770`).
- AnimCompleteCounter: the binary never zeroes it in UpdateAnimation and increments it on the chain path (0x80038D6C). The decompilation zeroes it on every animation or direction switch (`EntityManager.cs:222`).
- I did not re-check the report's third difference (the ApplyEntityForces shift).

## Open questions for the author

1. Climbing exit while sprinting: the binary climbs when the hero is blocked by a slope-6 cell while running Up (claim 14). Should SP1 include this, or leave it to the climbing work?
2. Should sprint dust on slopes 1, 2 and 4 use the water table (−0.25 × force, no dash/stop dust force), as the binary does? This only matters if SP2 is in scope.

## Suggested slice boundaries

The report's split (SP0 to SP3) holds, with two changes:

- **SP0** also calls CheckEntityInteraction (0x8002E910) in the Idle/Moving case before the tail, and keeps the three per-tick calls (0x8002F49C, 0x8002F768, 0x8002F884) before the state switch.
- **SP1 acceptance** adds two cases: the climb priority when blocked on slope 6, and the dash handler ignoring TryUseItem's result.
