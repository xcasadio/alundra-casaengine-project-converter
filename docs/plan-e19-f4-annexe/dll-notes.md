## 0. Summary

1. **The speaker never comes from Yarn.** The Yarn export has no speaker, name or portrait marker: the markers are `br glyph voice center slow flag yield empty`
   (`AlundraDialogueDirector.cs:345-371`); `voice id` is the blip voice (sfx 79 to 82) of a text, not an identity. `AlundraDialogueCapturePresenter.cs:71-76` only logs
   once if a Yarn line ever carries a `Speaker` (none in the corpus). The speaker comes from the **opcode operands and the entity state**: `0x0D` = the logic entity,
   `0x5C` = the first match of the search `v1`, `0xC4` = name from the operand `v2 | v3 << 8`, portrait from the first match of `v1` **[bin]** (section 1.2).
2. **The DLL ignores all of it today**: `AlundraEventProgramRunner.cs:935-942` (0x0D), `:1034-1037` (0x5C: `v[1]` ignored), `:1039-1045` (0xC4: `v1`, `v2`, `v3` ignored)
   all end in `OpenDialog` `:1880-1903`, which has no entity and no speaker parameter; `AlundraDialogueDirector.Open(asset, node, controlMode)` `:51`, `:243` has none either.
3. **The DLL field that carries `+0x68` already exists: `AlundraEntityScriptProxy.SpriteType`** (`AlundraEntityScriptProxy.cs:108`; written at spawn by
   `AlundraEntitySpawnFactory.cs:629` = `EntityRecordMapper.ResolveSpriteType` `:225-237`, `0` for the hero `AlundraWorldProxy.cs:1635`, `-1` when no header resolved,
   copied by `Clone` `:2361`). Binary: `InitializeEntity 0x80039D04` stores its 5th argument at `0x80039D70 sw $v0,0x68($s0)`; the decompilation's
   `SpawnEntity` passes `SpriteTableIndex | 0x100` for a map sprite (`GameEngine.cs:732-737`). `SpriteTableIndex` (`:94`) is the RAW record value and is not what the binary reads.
4. **The name text exists**: `AlundraEtcStringTable.TryResolveText(int, out string)` (`AlundraEtcStringTable.cs:128`, body `:162-200`) already resolves `Etc_0256..0511`
   to font3 text; 60 of the 256 entries of `0x100..0x1FF` are filled, 196 null, 0 empty string **[calc]**; all ASCII, widths 19 to 56 px (font3 advances), so
   `name_x = 64 + (112 - w) / 2` is in 92..110 and the clip's left edge (80) never cuts a real name. `AlundraFont3Advances.Advance(char)` (`AlundraFont3Advances.cs:70`) gives the advances.
5. **The portrait art is in the data, not in the export**: `DialoguePortrait` (SiImage shape, G0-R3) is in 331 sprite records of 184 map JSON of `data-extracted/` = **25 banks**
   (`Sector5Id` = record index in all of them; two are 48 x 72, banks 122 and 162), identical pixels in every map; `SpriteBankReader`/`SpriteWriter` read only
   `InventoryPortrait` (`SpriteBankReader.cs:235-255`, `SpriteWriter.cs:842-887`), so **no dialogue portrait is exported yet**. 24 new `.sprite` + 1 reuse (bank 15).
6. **The view is one more `TextBoxScreen` layer, not a new screen**: add `PortraitImage` (the inventory's idiom: rest position in the XAML, flight by bound render transform,
   MGUI ADR-0020) and `NameFrame` + `NameText` (the binary's name clip is a no-op, section 3.1) to `UI/Screens/TextBoxScreen.xaml`, bound to two new sub view models of `AlundraTextBoxViewModel`.
   `InventoryPortraitViewModel` (`AlundraInventoryViewModel.cs:102-188`) is reusable once its rest/size constants become per-flight values.
7. **MGUI cannot do the colour ramp**: `MGImage.TextureColor` (`MGImage.cs:220-230`) is multiplied (`MGTextureData.cs:21-22`, `Color * opacity`, 8 bits, max 1.0); the PSX
   vertex colour 255 is about 2x. Nothing per element selects a blend (`DrawSettings.BlendType.Additive` exists, `DrawSettings.cs:19-34`, no element uses it; `MGImage` swaps
   `DrawSettings` temporarily for its linear-downscale filter, `MGImage.cs:239-262`, `:499-511`, the precedent for the missing API). Inventory precedent: D2 = tint stays
   normal (`docs/plan-portrait-inventaire.md:92`, `:213`); never reported as a gap (`ai-agent/audits/mgui-gaps-from-xaml-screens.md` G1-G10 have no tint entry).
8. **Tests that move are few if the API is additive**: `AlundraTextBoxScreenXamlTests.cs:142-153` (children list) is the only certain mover; the rest depends on the shape
   of the portrait API (section 4).

### 1.2 What the binary does at the three call sites **[bin]** (re-read here, addresses of `ALUN_CD.EXE`)
- `0x0D` `0x8003D578`: `s0 = a0` = LOGIC entity; `if (lw 0x6c(s0) & 0x800000)` portrait `0x80057C84` (`0x8003D634`); then `lw a0,0x68(s0); jal 0x80059F6C` (`0x8003D640`); then `TryOpenDialog 0x800423F8`.
- `0x5C` `0x8003F01C`: `jal 0x8003C954` (search `v1`); **`beqz v0,0x8003F10C` skips BOTH portrait and name** when no match; else `s0 = g_matchingEntitiesBuffer[0]` (`lw -0x2728`), portrait if its flag bit, `lw a0,0x68(s0)` name (`0x8003F100-0x8003F104`).
- `0xC4` `0x80041DA8`: search `v1`; `beqz v0,0x80041EA8` skips both; match: portrait from `buffer[0]` if its flag bit; **name = operand `v2 | v3 << 8`** (`0x80041E8C-0x80041EA0`), not the entity's `+0x68`.
- The three calls to `0x80057C84` push the same constants (`0x800E4328`, `0x800E432C`) and the entity's `+0x114/+0x118/+0x11C` (position pointers, not values): the decompilation's NEGATED scroll in `Script_196_0C4` is not in the binary (consistent with the plan's 0.2.5 note).
- **Name open `0x80059F6C`** (`0x80059F6C-0x80059FCC`): returns without effect if `g_UIDisplayFlags (0x80180240) & 4` (a name box is already shown), or `idx - 0x100 >= 0x100` (unsigned), or the ETC pointer `[0x800C400C + 4 idx]` is null, **or the first byte of the string is 0** (the decompilation only tests null: `GameEngine.cs:2530-2560`); else stores `idx` (`0x80180288`) and `SetTransitionType(0xC)`. Close `0x80059FE0`: called ONLY from `0x80045F00` (the box's close trigger), followed at `0x80045F08` by the dialogue portrait return `0x80057B84`.
- Callers (static `jal` scan of the cached list **[calc]**): name open `0x8003D640`, `0x8003F104`, `0x80041EA0` only; dialogue portrait start `0x80057C84` from `0x8003D634`, `0x8003F0F8`, `0x80041E84` only; return `0x80057B84` from `0x80045F08` (box close) and the four inventory exits; name reset `0x8005A0C8` from `0x80044C28` and portrait reset `0x80057B64` from `0x80044C40` (both in the UI init just before `0x80044C5C`: map entry); `g_UIDisplayFlags` has **no other reader** than the name functions (`0x80059F6C`, `0x8005A0C8`, `0x8005A244`, `0x8005A3E0`: xref `uiflags_xref.py`, heuristic lui+offset scan) **[hyp for completeness]**: the name box looks presentation-only, so no logic trace should move.
- **Ordering quirk (fact, DLL consequence)**: the name/portrait opening happens BEFORE `TryOpenDialog`'s "already open" test, so a retrying `0x0D` of a speaker whose box is refused can still open a name box (guard `& 4`) and start the portrait (guard `state == 0`) while another box is open. D-E19-81 (fine details faithful) means the DLL call goes before the `director.IsOpen` check at `:1896`.

### 3.2 What MGUI can and cannot render
- Can: all of 3.1; `TextureColor` darkens (multiplies) and fades (`DA.Opacity`).
- **Cannot: the ramp 255 -> 128** (PSX vertex colour on a modulated textured quad: 128 = neutral, 255 about 2x; code byte `0x2C` = modulated `FT4`, `0x80057D88-0x80057D90` set r = g = b = 255): a multiply never exceeds 1, an approximation would darken the rest state. Gap to report (G11 of `mgui-gaps-from-xaml-screens.md`, French like its siblings): "an image cannot be drawn brighter than its texture". Missing API: `MGImage` property for brightness above 1 or a per-element `BlendType`/second additive pass (the `DrawSettings.BlendType.Additive` exists and the control already swaps `DrawSettings` for another purpose, `MGImage.cs:499-511`); XAML DTO `Image` (`Controls.cs:1264-1312`) has `TextureColor` but no counterpart. Until it exists: tint stays normal like the inventory (D2), the plan states it.
- No other gap found for the name box or the portrait. To be proven by pixel tests, not assumed: a name frame at x > 320 slid in a view with side bands draws nothing outside the view (the existing test covers Y only, `AlundraTextBoxPixelTests.cs:393-447`; ADR-0054), and a point-sampled scale-0 to scale-1 image.
