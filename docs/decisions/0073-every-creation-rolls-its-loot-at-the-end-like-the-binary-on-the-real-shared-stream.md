# ADR-0073: Every creation rolls its loot as its last act, like the binary, on the real shared stream

- **Status**: Accepted
- **Date**: 2026-10-16
- **Source**: this chantier: `docs/plan-e20-heros.md`, section 1.17 (E20.e0b, D-E0B-4, D-E0B-5, D-E0B-6, D-E0B-8; the author's answer Q-B1) and 1.17.2 (E20.e0b2, revisions 1 and 2, READY at its last closing review); evidence in `docs/plan-e20-annexe/e20-e0b/` (`oracle/`: `run_e0b2.py`, 25 checks, 9 140 vectors with 0 mismatch, `v8.json`, mutants; `e0b2-shadow.txt` for phase A and `e0b2-shadow-b.txt` for phase B); ADR-0063 to ADR-0066 and ADR-0072 for the creation sites and the stream

## Context

- In the binary, `InitializeEntity` ends with the loot roll `0x80032A40` (one caller, `0x80039F38`), through `ChooseRandomlyAnItem` (`0x80032968`) over the 2 048-byte table at `0x80028E0C` (octet `0x960C` of `ALUN_CD.EXE`, France). With an entity record, the flag word `f` (`hu +0x10`, forced to 0 when `(f & 0x7FFF) >= 0x800`) is kept at `+0x40`; when it is non-zero and its bit is raised in its bank (`0x8000` selects the temporary bank) the code is 0 and nothing is drawn; otherwise the code is the record's byte `+0x12` when non-zero, else the sprite header's `Contents` byte (`+0x1F`). Without a record `+0x40` is 0 and the code is the header's byte. A code `>= 0x100` gives 0; with bit `0x80` one step of the shared generator is drawn and the table row `code & 0x7F` is indexed by `state >> 28`, again; otherwise the item is the code when below `0x62`, else 0. At most two draws per creation.
- The DLL created entities at three sites (the map load loop, `SpawnEntityByRecordId` for `0x2D`, `0x8A`, `0x8B`, and `SpawnEntityBySpriteIndex`, which is also where the sword wave is born since E20.f3c) and drew nothing, so every number drawn afterwards (AI, opcodes, sparks) saw another stream than the binary's, and `ContentsItemId` / `ContentsGameFlag` were never filled.
- The number of draws of a map load depends on the tile of the hero during the load loop (the zone gate reads it): the tile set by `AdoptPlayerPawn`, before an arc places its own. The word after a load is therefore measured per (map, tile) pair (`v8.json`, 20 pairs taken from the `ArcSpec` of the suite).
- The slice was measured in two phases (as E20.e0b1): phase A put the whole code in place with the roll made only on the virtual register of the measuring sink (`4753357`), phase B made it real (`b5b2c88`).

## Decision

- **A pure class.** `AlundraLootRoll` (`Alundra/Scripts/AlundraLootRoll.cs`) holds the table and the two functions `Choose` and `Roll`; the draw is a delegate, so the class never touches the shared stream. It is called by the world, never by the static core of the entity factory nor by the record mapper.
- **One field and one line in the core.** `AlundraEntityScriptProxy.HeaderContents` (copied by `Clone`) is set by the single line `proxy.HeaderContents = header.Contents;` in the factory's `ApplyHeaderInitialization`. No `RecordContents` and no `HasRecord` field: the record code is read at the site of the creation (`RecordContentsByte`).
- **One private helper called once per creation, as the last statement of the `try` of each of the three sites** (after the push of the position to the root; at the sprite-index site just before the birth-tick marker block of ADR-0065, which cannot fail), so that a creation aborted by the error contract never rolls. The hero is adopted, not created by a site, and does not roll. In phase B the helper writes `ContentsItemId` and `ContentsGameFlag` and draws on the REAL stream (`AlundraRandom.Next`).
- **`ArcRun` re-seeds the stream before AND after `InitializeWithWorld`** (the author's answer Q-B1), and exposes `SeedAfterTheLoad` (the word read just before the second re-seed) and `HeroTileAtLoad`, so that the draws of a map load do not shift the arcs of the suite and a test can still pin the word a load leaves.
- **The comparisons of the apparition oracle that D-E0A-3 had excluded** (`+0x3C`, `+0x40`, the word after the call, from the seed `0x12345678` the oracle writes before each call) are added to the single full-path test `AlundraSpawnBySpriteIndexInterfaceTests.B2_TheFullPath_...`, in an assertion of its own, never in `SpawnProjectionAsserts.Check` shared with the tests of the e0a1 core.
- **Out of the slice** (still E20.e0c): the drop at death, its veto and the pickable object; the re-rolls of `0x8003A048` and `0x8003ABCC` (E14, O-E0B-2).

## Consequences

- The stream is now consumed at creation exactly as in the binary (map loads, `0x2D`, `0x8A`, `0x8B`, the interface); the `Contents`-less sword wave born in production passes through the helper and draws nothing, as the f3 oracle's `loot3c` 0 says.
- Tests: `AlundraLootRollTests` (9: 2 626 choices + 256 codes `0x100..0x1FF` + 52 + 183 + 12 + 6 011 vectors, 0 mismatch, table md5 `7c6b97ac50de72f436a6fbf08ed6bcd7`), `AlundraLootRollWorldTests` (M0 on 20 pairs, M1 to M7, the word after a silent load, the inertness of the helper without the sink) and the new assertion of `B2`. `Alundra.Tests` goes from 5 046 to 5 065 in Release and in Debug. **No existing test moved**, although the shadow of phase A predicted 248 (the draws and the words differ, but no assertion reads them: the reasons are in the README of the annex); `V = R` in the shadow of phase B (`divergent_draws` and `divergent_seed_reads` zero on 1 141 lines).
- Proof that the write is covered: with the body of the helper removed the suite is red on exactly M1 to M5 and `B2` (6 tests), nothing else. The 21 real mutants of the DLL code are all killed except one equivalent (the site's `& 0xFF`, which `Roll` repeats).
- `AlundraRandomShadow.OnVirtualRoll` and its two counters stay in production code, unused after phase B (the sink counts the real draws instead); removing them is a cleanup for a later slice.
- Known limits: the draws of the load depend on the tile of the hero at load, which the tests fix per pair; the map 167 has no `ArcSpec` in the suite and was measured at the new-game tile for an ad hoc spec.
