# ADR-0064: The entity slot table hands out the lowest free slot up to 63, and the spawned list follows the slots

- **Status**: Accepted
- **Date**: 2026-10-15
- **Source**: this chantier: `docs/plan-e20-heros.md`, section 1.16 (head, "Par défaut fidèle") and 1.16.2 (E20.e0a2, revision 1, READY at its second review); evidence in `docs/plan-e20-annexe/e20-e0a/oracle/out/v5.json` (the real `FindFreeEntitySlot` `0x80039AD0` and slot pass `0x80038634` of `ALUN_CD.EXE`, France) and in the shadow run `docs/plan-e20-annexe/e20-e0a/e0a2-shadow.txt`; ADR-0063 (the interface this table serves)

## Context

- The binary keeps its entities in one flat array of 64 entries (`0x80127FC4`, stride `0x294`). The hero is entry 0 and is never searched; `FindFreeEntitySlot` returns the first entry from 1 to 63 whose state (`+0x10`) is 0 and prints a message and returns null when there is none. An entity in the state 4 (destroyed) is NOT free: it stays busy until the slot pass at the head of the next `UpdateEntities` resets it to the template. Every pass of a tick (events, counters, lists, animation, physics, hits, `0x2C` searches) walks that array from 0 to 63, so the order in which entities are processed is the order of their slots, not of their creation: an entity that takes a freed low slot is processed before the older entities above it.
- The DLL had no table. `_spawnedEntities` was appended to in creation order by three paths (the map load, the adoption of the hero, opcodes `0x2D`/`0x8A`/`0x8B`), a fourth being added by ADR-0063 (the apparition by sprite index), and nothing capped it. Every pass of the DLL walks that list or one derived from it (`CollectTickEntities`, the counters, `BuildHitList`, the update proxies, `GetSpawnedEntityProxies`), so reordering the list is enough to reproduce the binary's order without touching a pass.
- The change could move pinned arcs, so it was done in two phases: a neutral shadow first (slots handed out, nothing reordered, nothing refused, every would-be reordering and refusal logged per test), then the behaviour. The shadow run over the whole suite (179 tests create entities, 5 502 assignments) predicted 11 out-of-order insertions in 8 tests and 112 refusals in one test; the highest slot of any test that only loads maps and runs scripts is 36 (the discovery's bound was 39).

## Decision

- **A per-world table of 64 slots** (`AlundraEntitySlotTable`, a 64-bit mask, one instance per `AlundraWorldProxy`, so a new map starts empty). Slot 0 is held from the construction, even in a world without a hero. `Allocate` returns the lowest free slot of 1 to 63 or -1 when full; `Release` ignores -1, slot 0 and anything out of range. The slot of an entity is `AlundraEntityScriptProxy.Slot` (default -1, not cloned).
- **The slot is taken before the creation and given back on any failure.** On the map load, `SpawnEntityByRecordId` and `SpawnEntityBySpriteIndex` the slot is allocated after the lookups the binary does first (the page lookup and the record lookup) and before the entity is built. A full table refuses: the map load skips the record with one warning, `SpawnEntityByRecordId` and `SpawnEntityBySpriteIndex` return null with one warning and add nothing. An invalid index is refused for the index before the table is consulted, as the binary checks the page first (oracle: only the page lookup's message, never the full-table one).
- **A destroyed entity keeps its slot until it is recycled.** `RecycleDestroyedEntities` releases the slot when it removes the entity, under the same gate (`GameplayBlockedMask`, 0x48) that already guards it: with the gate closed nothing is freed, as in the binary where the slot pass sits behind the same test. The gate was not changed.
- **The spawned list follows the slots.** An entity is inserted right before the first entry whose slot is higher; entries without a slot (-1: the test montages that fill the list by reflection) are skipped by the comparison and stay where they are; with nothing higher the entity goes to the end. The hero's adoption uses the same insertion with slot 0. No pass was modified; the comments that said "creation order" now say "the order of the slots". The engine's own list (`world.Entities`) keeps the order of insertion, which only matters for draw ties.
- **The error path honours "null, nothing added".** An exception after `_world.AddEntity` (the sound of the creation, the push to the root) removes the entity from the list, hands it back to the engine (`World.RemoveEntity`, which flags it for removal at the next update, the queued entity being integrated then dropped), clears its slot and gives it back to the table; the load skips and logs that record, the two methods return null. A test seam makes the path reachable (`CreationFaultHookForTests`, and `SlotTableFactoryForTests` for a world that starts with held slots); both are static, null in production and reset by the tests.
- **The root of the chain of parents is written by the record path too.** `ChildEntity = parent.ChildEntity ?? parent` for a non-null parent, now shared by both creation paths through `ResolveRootEntity` (it was the interface only; the binary writes `+0x08` for both halves of `InitializeEntity`). No reader is known, so nothing visible changes.
- **The shadow channel stays**, inert without the environment variable `ALUNDRA_SLOT_SHADOW_LOG` (nothing written, nothing allocated): it logs out-of-order insertions and overflows per test with the outermost `Alundra.Tests` frame of the stack.

## Consequences

- Two existing tests move, both in the shadow file and both explained by the slot order or a refusal. `AlundraInoaDayOneArcTests.A11` (shadow: one out-of-order insertion, slot 1 below a highest live slot of 12): record 0 of map 164 is destroyed, so the record 4 spawned by `0x8B @95` takes slot 1 and is now processed BEFORE Septimus (slot 2); its `C[3]` waits for the flag T3 that Septimus's `C[2]` sets at `@437`, so it now leaves the wait one tick later and deactivates at the next frame, the test running that one frame. `AlundraSpawnBySpriteIndexInterfaceTests.B2` (shadow: 112 overflows) made 156 apparitions in one world; each vector is now recycled once checked, as the binary frees the slot of a destroyed entity. Nothing else moved: the seven other tests with an out-of-order insertion pass unchanged.
- Proved: 17 allocator tests copied from the oracle's V5 lines (five apparitions, a state-4 slot busy until the pass, reuse after the pass, the full table of the hero plus 63 with the 64th and 65th refused, lowest-first after freeing 40, 9, 21, the new lines "invalid index with a full table" and "apparition in loop 2 in a recycled slot"), and 15 world tests on map 14 (slots of the loaded entities, order after a recycle, slotless entries, release timing and the closed gate, the refusal on the three paths, the load with a nearly full table, the fault path on the three paths, `ChildEntity` on both paths). `Alundra.Tests`: 4 775 before, 4 807 after in Release and in Debug.
- Known limits, deferred: stale pointers are not ported (a recycled entity keeps the identity of its object, D-E0A-7); the serial `+0x04` is not written; the participation of a new entity in the tick it is born in is E20.e0a3; the loot roll at creation is E20.e0b. The map load fills slots in record order and the hero is slot 0, so a map with more than 62 loaded records (75 and 92 by the discovery's census, loaded by no test) would now skip its last records with a warning, as the binary would refuse them.
