# ADR-0063: The apparition by sprite index takes Z in the DLL's frame through a record-less core and checks each page against its own table

- **Status**: Accepted
- **Date**: 2026-10-15
- **Source**: this chantier: `docs/plan-e20-heros.md`, section 1.16 (head, decisions D-E0A-1 to D-E0A-5) and 1.16.1 (E20.e0a1, revisions 1 and 2, READY at the closing review); evidence in `docs/plan-e20-annexe/e20-e0a/README.md` and its oracle `oracle/out`; ADR-0026 (the DLL's Z is the binary's minus one), ADR-0062 (`BankKey` and the valid indices of each map)

## Context

- `SpawnWarpEntity` (`0x80039F58`) has 102 call sites in `ALUN_CD.EXE`: the hero's shot, the use of items, the loot, the enemies' handlers. It looks the sprite up by (page, index) with `0x80039B28` (the page is part of the key: the same number exists on both pages), takes a case with `0x80039AD0`, then creates the entity with the half of `InitializeEntity` (`0x80039D04`) that has no registered record. Nothing in the DLL could do that: an entity was only ever created from a record of the map.
- The Z a caller passes is not the Z a DLL entity holds. The binary computes `PosZ = Z - ModZ + 1` and raises it to `terrain + 1`; the DLL keeps the binary's value minus one raw unit everywhere (ADR-0026). The shot passes `Z = hero.PosZ + (ptr[3] << 16)` read in the DLL's frame, so the binary's argument is that plus one: an arrow spawned at the Z of the hero is one raw unit above him (oracle: raw 2 in the binary, 1 in the DLL), and one raw unit lower without the unit. The record path has no such unit, its Z coming from the map's height byte.
- The validity of an index is per map for the map page (a number is valid only on the maps whose table holds it) and per catalog for the global page. The binary's rule, measured on the real code over 483 maps x 256 indices: `0 <= index < 256` and an entry in `0x80000000..0x801FFFFF` (-1 and 0 are invalid); 2 507 valid pairs, 65 empty maps, at most 22 per map, 244 numbers with one creation image each.
- The binary writes `+0x08` (a root: the parent's own root, else the parent) next to `+0x0C` (the parent). The DLL had a field `ChildEntity` (the name the decompilation gives to that word) that nobody wrote or read.

## Decision

- **A record-less core.** `AlundraEntitySpawnFactory.CreateEntityFromSpriteIndex` builds the entity from a prefab (a bare entity when none) and a sprite header, callable without a world. It shares with the record path the header half of `ApplySpawnInitialization`, extracted unchanged as `ApplyHeaderInitialization` (flags, programs, body box, `PosZ - ModZ`, the raise to the terrain, the pending first animation); the lines that read the map's tile data stay with the record path. No record means: `EntityRefId = -1` (the field's default 0 would answer `0x2C [0]` and `0x2E [0]`), `EventTrigger = -1`, no program codes, `SpriteTableIndex` the raw index, `SpriteType` the binary's identifier (the index, plus `0x100` for the map page), the palette and the sheet not stored (nothing reads them).
- **Z in the DLL's frame, the unit added by the interface.** `IEntityWorldContext.SpawnEntityBySpriteIndex(parent, isMapPage, index, x, y, z, direction)` takes the Z a caller reads in `PosZ` and passes `z + 1` to the core; the core takes the binary's argument, so the record path shares it without the unit. A constant of the binary is passed minus one. (D-E0A-1, D-E0A-2)
- **A member of `IEntityWorldContext`, default null.** Every existing implementer keeps compiling; `AlundraWorldProxy` implements it and returns null, with one warning line and nothing added to the world, for an index outside 0 to 255, a number the current map's table does not hold, a sprite the catalog has no prefab for, or a prefab that cannot be read. The caller must test the null (the binary writes through it). (D-E0A-2)
- **The root in `ChildEntity`.** `ChildEntity = parent.ChildEntity ?? parent`, only for a non-null parent, with a comment that the decompilation names it so and no reader is known. (D-E0A-4)
- **Validity per page, per map, lazily.** The global page is valid where the catalog has the bank key `alundra_N`; the map page where `Data/map-sprite-indices.json` holds the number for the current map (a map the file does not know is refused) and the catalog has the bank key `N`. The file is read at the first call of the interface, never at the load of a world; if it is missing the table is permissive with one warning and the bank key alone decides. `SpriteRecordCatalog` reads `BankKey` (tolerant when absent) and answers `TryGetPrefab(isMapPage, index)`.
- **The creation roll is out.** 54 numbers (6 on the global page, 48 on the map page, `Contents & 0x80`) draw at least one word of the generator and write `+0x3C`/`+0x40` at creation; this is not ported here and those fields are excluded from the comparison (E20.e0b closes it). (D-E0A-3)
- **Appended to the end of the spawned list, no case.** The case, the cap of 63, the order of the passes and the participation in the birth tick are E20.e0a2 and e0a3; no production path calls the interface in E20.e0a1.

## Consequences

- Proved against the real binary, with nothing computed by the tests: the oracle's rows (`docs/plan-e20-annexe/e20-e0a/oracle/out`) give the projection of 395 creations (151 + 244), 109 geometry vectors (the Z rule, the raise to a raised terrain, the offset-Z prefabs above the ground, the three parents) and the 8 calls the AT9 traces journal at the shot, compared to the core without a world; the full path on map 14 (151 global numbers and the 5 map numbers valid there) gives the same projection except the terrain-dependent fields, which the flat field of the oracle proves at the core. The equivalence of number 79 of the map page by the interface with record 0 of map 14 by the production path differs only by the closed list (EntityRefId, the record's height, the parent and the root, the self pointer).
- The suite is untouched: 4 752 tests before, 4 775 after in Release and in Debug (23 added, no existing test changed), the traces unchanged.
- Known limits, deferred: no case (the 64th apparition is not refused yet), no tick of birth (the entity ticks from the frame after its creation, so a shot cannot move in the tick it is fired in), no creation roll, the first animation switch is pending as for a record, and the terrain-dependent fields are proved at the core on a flat and a raised field, not on every map.
- A caller passing the binary's Z unchanged would put the entity one raw unit too high; the interface's documentation and the test of the AT9 calls (binary 1 048 577, DLL 1 048 576) pin it.
