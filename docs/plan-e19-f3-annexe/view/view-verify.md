## 2. The stale-layout gap, measured by me (corrects the size of the report's gap)

Run through the stand-in stack, engine frame order, the real machine and the proposed presenter (`dyn_*` files, `comp\dyn_analyze.py`, `comp\guard_analyze.py`). The first drawn frame of the SECOND choice shows the layout of the last UI update of the window before it was removed:

| first choice ended by | what the next choice's first drawn frame shows | texels |
|---|---|---|
| completed (slide-out to its end) | nothing (stale layout is the off-screen one, x 320) | 0 |
| very first use (fresh window) | nothing (never laid out) | 0 |
| cancelled mid slide-in (my case: stale frame x 253) | the old frame, one frame | 1898 (bbox x 253..319, y 137..175); the report's 2388 matches a cancel while the layout is at x 234 (my compositor: 2393 non-background texels at that layout) |
| **cancelled at rest** | **the whole box at rest, cursor and both labels** | **3556** (bbox x 176..303, y 138..175) |
| cancelled mid slide-out (stale frame x 224) | the old frame | 2657 (bbox x 224..319, y 137..175) |

So the defect is not limited to "cancelled mid-slide": the at-rest case is the worst and the likeliest, since a pending choice mostly waits at rest for the pad. Cancel paths in code: `AlundraDialogueDirector.Open` (`:258`, "a choice still waiting is dropped"), `InstallForMapEntry` (`:240`), `CancelChoice` (save book abandon / reset, `AlundraSaveBook.cs:411`); `CloseStandaloneChoice` (`AlundraSaveScreenDirector.cs:359, :1032`) runs after the answer is taken, so on a closed machine: no flash. Whether any of them happens in play with a choice up is not established (same as the report).

A cheaper guard than "park the view model off-screen for one more pushed tick before removing", tested: in the tick that pushes the screen, after `Apply`, set `RootVisibility = Collapsed` once (the next tick's `Apply` sets it back to Visible). Result in the four scenarios above: the first drawn frame is empty (0 texel), every other frame is byte-identical to the unguarded run (only that frame differs: f14, f25, f31; no frame differs in the completed case), and the normal paths (fresh window, completed choice) already draw nothing on that frame, so it costs nothing there. It is a presenter-side hold that works around the engine's update order (O-E19-65), so by the author's rule (report the gap, never work around) it stays the author's call; I only measured it. `V\probe\Program.cs` (env `VP_GUARD=1`), outputs `V\out\dyn1_*`.
