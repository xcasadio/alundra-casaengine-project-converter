## 3. Corrections and additions (things that can change the plan)

### 3.1 map 260: the program C[5] runs on TWO entities
Records 16 (`I76_Testament d'Anzes`, 24x16x16, flags 0x200180, controller) and 17 (`I33_Armure brisee`, point, flags 0x230180) both reference A[2] and C[5]
(slots 130 and 133). The `0x20 [32,0]` @747 therefore also runs on a controller entity. In the binary both behave identically (real code: `63 [128,128,1]` clears 0x180 on the logic entity
itself - selector 0x80 = the caller's logic (0x8003C954 group 0 stores `s3 = a0`) -, `1B [128,0]` +32768/tick, 64 calls, 32 px). For the plan: one program, two entities, only one controller-less.
By strict census the `0x20` population is: 260 sites on controller entities, 4 on the hero only, 1 controller-less (47), 1 mixed (260); all 16 `0x21`, 16 `0x22` and the `0x23` on controller entities.

### 3.2 `0x22` literal target: tick-exact for ascents, one tick EARLY on descents (one site)
The report says the literal target is "exact in every convention". True for reachability and for ascents, not for timing on a descent. Real code (`t_desc.py`):
ascent 208 px -> 304 px (+32768): binary 192, DLL literal 192, DLL shifted 192; ascent 0 -> 240 px (+65536): 240 / 240 / 240; **descent** 112 -> 48 px (-32768): binary 129, DLL literal **128**, DLL shifted 129;
descent 240 -> 176 px (-65536): binary 65, literal **64**, shifted 65. Reason: the binary sits at `X+1`, so after the full steps a descent is 1 unit above the target and needs one more (clamped, -1) step; a literal target in the DLL convention is hit at the last full step.
Only ONE of the 17 sites descends: **115 B[2] @367** (`1B [128,255]`, block rec19 `Bloc transparent`, 48 px home, off-chain). Real code on map 115 (`t115.py`): the same block rises 160 px (`20 [160,0]` @220, 320 ticks), then `22` returns at the 321st call after the first (last steps ... -32768, -1, 0), so a literal DLL target ends at call 320. The shifted target `(H<<19)-1` (48 px < 256 px, float-exact) reproduces 321; at 304 px (127 rec17/18, ascents) only the literal target works. A per-site/per-direction rule or an accepted 1-tick drift on 115 are the two options; neither is a product question.
All other 0x22/0x23 sites are ascents (`1B` before the site: 127 x12 `[128,0]`, 89 @663 `[0,1]` ... checked in `sites22.py` and the `last 1B` listing); map 36 @1252 is a `0x23` ascent at +16384/tick (12 hanging ceilings, 240 px), whose end can also come from the Z contact; its dynamics were not analysed by either report.

### 3.3 `1B` on controller-less entities: more sites than the two Z waits, all but two are no-ops
Logic-entity `0x1B` sites with a controller-less candidate: 47 @439/@445 (rec3), 260 @744/@753 (rec17), 117 @1077 (rec21), 136 @116 (rec0), 137 @100 (rec0), 396 @2049 (rec5). The four non-47/260 sites all write `1B [0,0]` after `17` or `63 [128,0,1]` (gravity cleared) on the key-trigger prefab: no motion. `0x17`: 47 @426 and 117 @1076; no controller-less candidate for `0x15`, `0x16`, `0x25`, `0x70`, `0x21`, `0x22`, `0x23` (census_ops.py). So the only controller-less entities that ever move in Z are 47 rec3 and 260 rec17 (`census_ops.py`).

### 3.4 `IsOnGround` readers in the DLL
The report lists `0x25` and `0x70` only. `AlundraEntityScriptProxy.cs:1409` also reads `IsOnGround` for `EntityFlags.DeactivateOnImpact` (0x10, "slot E as soon as it hits something"). No controller-less prefab has 0x10 (low flag bytes of the 6 used prefabs: I33 0x80, Laser 0x02, Sara 0x80, Rancune 0x00, key trigger 0x80, Nirude 0x00), so nothing moves, but the list in the plan should name it.

### 3.5 Other small additions
- 4 no-gravity controller-less records spawn BELOW their terrain (map 36 rec21/31/40/41 "Laser (?)", z 16 px, T 32 px); the binary spawn clamp lifts them to `T+1` (0x80039EE4-0x80039F04). The report only counts the 8 that float above terrain.
- The binary does not clear `Parameters[1]/[2]` at program start (0x80041EE4 writes only `+0`/`+4` of the state); the DLL clears them at init. A wait interrupted and re-entered at the same address would see a stale memo in the binary. No corpus Z wait depends on it (the closed list runs once). Not verified at corpus level.
- Animation impulses: `+0xF8` is zeroed every `UpdateAnimation` call (0x80038AE4) and set only on a switch (0x80038B64). None of the 6 used controller-less prefabs has an animation with `IsZForceApplied != 0` (`74db711f` has one but no record uses it), so the impulse branch is inert for them. Several of those prefabs have animations with Speed != 0 (XY forces), which the pure-Z assumption (claim 14) excludes.
- `0x15` (Reset z pos, 0x8003D710) writes `PosZ = ((Height<<3) - ModZ) << 16` with no `+1`: the same record target as `0x22`. No corpus site on a controller-less entity.
- `0x63`'s selector 0x80 (and `0x43 [0x80]`) means "the logic entity itself" (a0), not "the owner" when logic differs.
