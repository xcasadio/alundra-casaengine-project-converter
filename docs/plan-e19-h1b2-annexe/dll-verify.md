## Corrections

C1. IsOnGround is not set by the support snap of a controller-less entity (claim 9). R-STEP must write it on both found and landing (the report already says so); the "today" description is what is imprecise.

C2. The impulse is unspecified in R-STEP. `IsZForceApplied` is written for every entity, controller or not ("This holds for an entity without a sprite or a clock too", AlundraFrameSyncPasses.cs:205-217, `GiveImpulse`), and consumed only in the `Controller != null && !immediateAtSpawn` block (ESP:685-694). "Same decay as a controller NPC" must say whether that block (impulse then decay, R1-R3) is shared. In production it is inert: none of the 6 controller-less prefabs has an AnimSet with `IsZForceApplied != 0` (checked in sprite-records.json). In tests a bare entity carries a real header: the A1c crates have 1024 on anims 1, 3, 4, and the map 390 programs only select anims 5, 0, 13 and `0x59 [129,0]`, so A1c stays inert. State it in the rule so a later bare-with-header test does not jump.

C3. "two rules" for landing: three families already exist. The hero state uses the strict test `PosZ + F < T` (ASM:231, 346), controller NPCs keep `<=` only for the engine's 4 px snap (D-E19-40), the harness uses the binary's `<=` in binary convention. The 4 px snap does not exist for a controller-less entity, so the strict test is the binary-exact rule in the DLL convention for it and adds no "new" semantics beyond the hero's. If strict is chosen, IsOnGround must be position-based (`PosZ + ModZ <= floor`, as ASM:215) and not "landing happened": a no-gravity entity resting at T with F=0 is not a landing under strict but is `IsOnGround = 1` in the binary (`0x800380F8`: `!(FloorHeight < PosZ)`). With `<=` it falls out of the landing branch.

C4. Binary 0x80038364 order, for the plan: clear +0x168/+0x140/+0x13C, force pass `0x80036828` for all, MoveEntity per entity (`0x80037E34`: Z before XY), then `0x80038064` per entity: FloorHeight, `IsOnGround = !(FloorHeight < PosZ)`. The DLL's order for a controller-less entity (XY in RunOneKinematicTick, Z in EvaluateEntitySupport after it) is XY then Z. The binary steps Z first, on the terrain under the position BEFORE the XY step (ComputeZPosition reads `ComputeEntityGroundHeight` at the current XY, then ComputeXYPosition moves); the DLL's controller-less entity steps XY in RunOneKinematicTick and Z afterwards in EvaluateEntitySupport, so its terrain probe is taken at the position AFTER the XY step. Same family as O-E19-28 ("Z des PNJ en retard d'un tick"). It only matters for a controller-less entity that moves in XY and Z in the same ticks: none of the 67 records does (the 47 and 260 programs write Z only: Sara's only speed anim is 6 and the armour's is 1, and neither program selects them during the fall or the lift; the scan is a fall-through scan of 0x1A/0x59 not run in a world).

C5. Rising controller-less entities have no ceiling test (the binary's `CheckEntityCollisionUp`, `ComputeZPosition` 0x800375E0, runs for every rising entity; the DLL has `TryFindCeiling` for the hero only, ASM:346). Same gap as controller NPCs today. Armour 260 rises 32 px with nothing above (no collidable in the footprint was found by header geometry alone, not run). List it as a known deviation, not a risk.

C6. Stale doc to update beside the comment at runner :721-724: the XML doc of `WaitZDistance` (:2471) says "0x21, which is the only caller dispatched so far".

C7. Minor lines: default label 1853 not 1852; gate 772 not 770; terrain local ESF:663 not 662.

## Missed by the report (decision relevant)

M1. The binary is one-sided on 0x22 (claim 4): the plan's rule must reproduce "no force of the wrong sign is created", and its test must include a start with ForceZ of the opposite sign (stall, as the binary) so nobody "fixes" it.

M2. 0x22 first call without a record (hero or bare test proxy): binary prints and then reads memory at address 9 (`lbu 9($s0)` with `$s0 = 0`). The audit probe (`ProbeOpcode`, AlundraStoryChainOpcodeAudit.cs:89-120) runs `[op, 0xFF]` on `new AlundraEntityScriptProxy()` and treats any exception as "ported", so any no-record behaviour (return 0 and memo 0, or throw) leaves `IsPorted(0x22)` true. No site exists; pick "wait forever with a one-time warning" or document the throw.

M3. Gravity crates stacked on map 390 now become supported every tick (claim 25). The A1c pins are on PosZ (unchanged) but `CollidedWithEntityZ` and `IsOnGround` of 6 crates flip 0 -> 1; any `0x6F`/`0x70`/`0x25` on them would see it. None found in the 390 programs (0x1A/0x59/0x1B/0x5E/0x20-0x23 scan), so A1c should stay green, but the plan should name it as the only visible effect.

M4. The `Collidable` controller-less records (key triggers, 21; flags 0xa080) run `TryFindSupport` today with the unclamped seed; under R-STEP the seed becomes `max(modded+F, T+1)`. With no gravity and F=0 both are >= modded, and the candidate must be strictly below modded, so it is never found, before or after: unchanged (185 rec10 floats 16 px above T and stays).

## Bottom line

All decision-carrying claims hold except: the "not certain" status of 115/388 (they are controller-driven; the set of controller-less waits is exactly {47@442, 260@747}) and the description of IsOnGround on a support snap. Add C2 (impulse sharing), C3 (hero strict precedent, IsOnGround rule), M1/M2 (one-sided clamp, no-record) and M3 (A1c crate flags) to the plan.
