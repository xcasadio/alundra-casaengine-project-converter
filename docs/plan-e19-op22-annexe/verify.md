## 1. Confirmed
1. **Handler** (disassembly): first call stores `byte(rec+9) << 19` at `state+0xC` and returns 0 with no test (a null record is printed then read, `lbu 9(0)`);
   later calls: exact `bne target, PosZ(+0x11C)` (not `+0x1E0`), `gap = target - PosZ` computed in the delay slot, one-sided clamp of ForceZ(+0xB8) (gap > 0: only if `gap < ForceZ`; gap <= 0: only if `ForceZ < gap`),
   never creates or reverses a force. `0x23` calls it then returns 1 when `+0x140 != 0`, also at the first call. Matches the C# port line for line.
2. **Frame**: `FinalForceZ = ForceZ` (`0x80036BB8`); air step `PosZ += F` (`0x80037708-14`); landing iff `ModdedPosZ + F <= T`, then `PosZ = T + 1 - ModZ` (`0x80036C20-34`, `0x800376F0-FC`);
   spawn `PosZ = z - ModZ + 1`, floored at `T + 1` (`0x80039EA0-F04`) with `z = Height << 19` (same value as the 0x22 target). So every binary rest/spawn position is +1 and the 0x22 target is not: the shifted target is the binary comparison in the ADR-0026 frame.
3. **Own model** (`model.py`, 60 000 random waits, constant force, no terrain): shifted target = binary in 100 % (call count AND end position in the frame), also on misaligned arrivals; literal differs on aligned descents
   (6557/14900 with my force set: those where F divides the distance) and on a few ascents (distance = 1 mod F); `dir` (literal up / shifted down) differs on 19 ascents. 115: binary 321 calls end 3145728, DLL literal 320, DLL shifted 321 end 3145727; ascent H20 160/160/160.
   (The report's "6803 of 6803" depends on its force set; the direction of the claim reproduces, the exact ratio does not.)
4. **Binary call counts at the 17 sites** (report's driver, run by me): 127 H20 and H12 = 160, 127 H30 and H38 = 192, 89 = 68, 363 = 48, 36 C[4] = 160, 36 C[14] `0x23` = 0, 115 = 321; literal gives 320 at 115 only; shift and hyb give the binary count everywhere.

## 2. Refuted or corrected
- **"A DLL-only rule cannot satisfy D-E19-94"** is overstated. No DLL-only SHIFTED rule is safe (point 6), but option (C) the report itself lists (literal + one extra no-op call after an aligned descent) is DLL-only, exact on the call count at the 17 sites AND keeps the exact absolute end pose of the binary (3145728, 10485760...). What is true: only the shifted (frame-consistent, general) rule needs the engine. The author's choice should be put as "exact general rule + engine setting (A)" versus "exact at the 17 sites, DLL-only, a fit (C)".
- **Engine ADR "0057" and parent ADR "0040" collide.** Parent: the plan (`docs/plan-e19-opcodes.md:8130`) already reserves "next free number, 0040 today, to recheck" for the G1 effects-export ADR. Engine: O-E19-74 (`:10002`) says the engine's 0056 exists twice and `chantier/audio-modern` already holds 0056-0060, so G2d is to be renumbered 0061 and the next ones taken after the last number of both lines, rechecked before each commit. The plan must say "next free number, rechecked before the commit", not 0040/0057.
- **"I could not run `CasaEngine.Tests` in the scratch copy (it needs the editor projects)"**: from a `git archive` copy of HEAD with the three submodules, `CasaEngine.Tests` builds (0 errors) with `dotnet build CasaEngine.Tests/CasaEngine.Tests.csproj`; the engine acceptance (build explicitly, the .sln excludes it) is feasible in a scratch copy.
- Minor: "7 uses of the const" = 6 uses + 1 declaration (point 9). The "6803 of 6803" ratio is model-dependent (point 3).

## 3. Missed items and plan impact
1. **ADR numbering** (above): the plan task must not hard-code 0040 / 0057; two other plans (G1 parent, G2b-1/G2b-2 and G2d engine) compete for the numbers (O-E19-74).
2. **Engine closed list is incomplete.** `CasaEngineMonogame/AGENTS.md` section 10 (docs when a public API is added) -> `docs/engine/character-controller-features.md` has the settings table (`:161-162`, `GroundSnapDistance`, `StepHeight`...): a row for the new setting. The serializer round-trip test lives in `CasaEngine.Tests/EditorServices/CharacterControllerComponentSerializationTests.cs` (`StepHeight` at `:43`, `:76`), which the report does not list (it lists `CharacterControllerSettingsTests`/`ComponentTests`). The engine work is more than one commit, so the engine repo also needs its own plan file `ai-agent/tasks/<subject>-tasks.md` (the parent plan alone is not enough); the plan should name the engine branch (the submodule is on `chantier/e19g2d-overlay-blend`; `chantier/audio-modern` is the author's).
3. **Blast radius of the proposed setting.** The per-controller minimum at 0 on EVERY factory-spawned controller also lifts the threshold in `Update`'s inherited-ground-displacement (`:258`, `:277`) and the horizontal `:1384`, i.e. every sub-0.001 px step of every NPC, not only the vertical scripted one. Measured neutral on all tests/arcs (my engine-0 suite run included the hero), but untested on the author's recipe. A narrower variant (set the minimum to 0 only around the vertical `Controller.Move` of `MoveVerticalAndPullPosition`, or an engine overload for a vertical-owned Move) would keep the horizontal paths bit-identical; worth offering with (A). Default bit-identity: `0.001f * 0.001f` is not the old `0.000001f`; a displacement of exactly 0.001f flips from applied to dropped (not reachable with `n / 65536f`).
4. **Riders never exercised.** In both the report's and my 36 C[4] probe the hero is "placed" on the landed platform but is not carried: it ends at the terrain (PosZ 1048576, 16 px) while the platform rises (my `probe-out/s36c4_rec3.*.txt`). So "an entity resting on the platform keeps its pose" is argued, not measured. By the code the hero's support top is `P + Depth + 1` in both rules (1.5e-5 px lower with the shift, a float root), and NPC riders (pixel-truncating `PushLogicalPositionToRoot`) would drop one whole pixel, but no site has an NPC rider and 36 C[4] warps right after the wait (`53` at 497). Low impact; keep it in the ADR consequences (rider pose, `TileZ` of the platform one below the binary's `H >> 1`, ADR-0026's "pixel and TileZ do not change" premise no longer holds at a 0x22 end pose because the binary lands on `Z = 0 mod 65536` there).
5. **Dead 0x22 sites not listed**: the raw census finds 22 sites, 5 more than the 17: 178 @386 (known dead), 12 C[1] @728, 127 C[1..3] @191/@217/@245 (reachable from a table entry but no record owns the program, no `0x40` binds them: 127 has one `0x40 [2,0]` at 171 that unbinds). The report only discusses 178. No plan impact; the plan's "16 reachable + 1" stays right, but the annex should list the five as dead.
6. **Real-site tests must set the hero/flag montages the report used** (hero tiles, flags 32769 / 32774 set after the map load, dialogue button for 115); my probe reused them and they work (33/33).
